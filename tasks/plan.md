# Implementation Plan: Local Ollama Embeddings

## Scope and model choice

Move LightRAG embedding inference to Ollama in this Compose stack. The selected model
is `bge-m3`, with 1,024-dimensional embeddings. `BAAI/bge-reranker-v2-m3`
is a query–document scoring model, not an embedding model; using that exact
model would require a separate reranking integration and serving-compatibility
investigation. Authorization to implement the proposed plan selects `bge-m3`.

Chat and LightRAG extraction/keyword models retain their current providers.
Ollama is now a pinned Compose service with persistent `ollama_data` storage,
no published host port, and an `ollama-init` service that downloads `bge-m3`
before LightRAG starts. The host Ollama installation is unchanged.

## Task 1: Verify local serving and storage

Dependencies: None. Scope: read-only inspection.

- Inspect the installed Ollama version, running service, listen address, and
  available models. Initial sandbox connection failures were resolved by
  authorized elevated inspection; the host service is running.
- Check the pinned LightRAG version for OpenAI-compatible embedding support
  with Ollama and for workspace isolation of every configured PostgreSQL store.
- Inspect whether the current `company` workspace contains indexed documents.

Acceptance: identify a supported endpoint, model name, vector dimension, and
safe index-isolation method without printing credentials.
Verification: read-only service, API, version, and storage checks.

## Task 2: Make Ollama reachable and prove embeddings

Dependencies: Task 1. Scope: stack service and
temporary container connectivity check.

- Pull `bge-m3` if absent.
- Add Ollama and a model initialization service on `knowledge_api`. Use
  `http://ollama:11434/v1` for container connectivity without a host port.
- Test `/v1/embeddings` with a short input and a placeholder API key; verify a
  finite, nonempty vector of length 1,024. Check document/query embedding support
  and request-size compatibility with LightRAG.

Acceptance: a container can obtain a valid embedding from the host model.
Verification: actual embedding request from the Docker network.
Checkpoint: stop configuration rollout if this compatibility check fails.

## Task 3: Configure an isolated index

Dependencies: Tasks 1–2. Scope: `compose.yaml`, ignored `.env`, `.env.example`.

- Keep the OpenAI-compatible binding if verified, and configure:
  `EMBEDDING_API_BASE=http://ollama:11434/v1`,
  `EMBEDDING_API_KEY=ollama`, `EMBEDDING_MODEL=bge-m3`, and
  `EMBEDDING_DIM=1024`. Keep `EMBEDDING_SEND_DIM=false` and use
  `EMBEDDING_USE_BASE64=false`.
- Make workspace selection configurable and choose a fresh workspace for
  `bge-m3`, only if all storage backends safely isolate different dimensions.
  Otherwise provision isolated storage according to the pinned version.
- Preserve the old index and source documents. Verify sample ingestion first;
  bulk reingestion of the large existing corpus awaits the user's cost/scope
  decision. Do not reuse vectors generated by the old embedding model.

Acceptance: Compose resolves correctly and new vectors cannot mix with the
old index. Provider keys for chat/extraction remain unchanged.
Verification: `docker compose config --quiet` and inspection of effective
nonsecret settings and index isolation.

## Task 4: Validate retrieval and document operation

Dependencies: Task 3. Scope: `README.md`, live validation.

- Restart/recreate the affected LightRAG service with the new configuration.
- Ingest a small sample into the new index and run a known-answer search;
  verify relevant sources and absence of embedding dimension errors.
- Run the bridge unit suite and `docker compose exec mcp python smoke.py`.
  Live ingestion/search may call the existing extraction/keyword provider and
  incur provider charges even though embeddings are local.
- Document Ollama setup, host connectivity, model/dimension, index migration,
  and rollback. Preserve existing unrelated README edits.

Acceptance: retrieval through MCP works with locally generated embeddings,
checks pass, and setup/rollback instructions reflect the deployed behavior.
Verification: Compose validation, bridge unit tests, live ingestion/search,
and MCP smoke check. Record any live check that could not be performed.

## Rollback and risks

Record the previous nonsecret embedding settings and workspace/storage target.
Rollback restores both the previous provider configuration and old index, then
recreates LightRAG. Never delete persistent volumes as part of this change.

Primary risks are incompatible embedding requests, host network reachability,
insufficient memory or slow CPU inference, and storage collisions between
different vector dimensions. Verify these before bulk reingestion.

## Implementation results

- Compose-managed Ollama 0.34.2 is pinned to the Linux amd64 image digest.
- A two-input container request returned finite, nonzero 1,024-value vectors.
- LightRAG 1.5.7 creates `bge_m3_1024d` vector tables and scopes document,
  status, and graph storage by workspace. The old `company` index remains.
- The previous `.env` and all 11 original document sources were preserved with
  restrictive permissions in ignored `backups/` paths. The corpus contains
  9,341,203 characters, with 9,098,186 in the largest document.
- Compose validation and all three mocked bridge unit tests passed. Tests ran
  inside the existing MCP image using its pinned dependencies and temporary
  files, without paid API calls.
- Sample ingestion completed; MCP health, protocol, and live search passed.
  Live search returned Giulia Bianchi Demo and the `demo-acme.txt` source.
  Sample extraction and live keyword search used the configured paid provider.
- The existing ingestion workflow also submitted additional documents to the
  new workspace during verification; it was left running.
- README setup/migration/rollback instructions and environment initialization
  messaging were updated. No database volumes were removed.

## Open decision

This does not block operation of the new stack or new document ingestion.
